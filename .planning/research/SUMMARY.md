# Research Summary: iso-agents
**Domain:** in-isolate coding agent runtime | **Researched:** 2026-10-10 | **Overall confidence:** HIGH

## Executive Summary

All four research files converge on one architecture: a single Cloudflare Worker run under `wrangler dev` (real workerd, no Cloudflare account), containing a request-scoped agent loop — prompt → LLM → in-memory VFS write → in-isolate type-check → transpile → QuickJS-WASM sandbox execution → spec assertions → error feedback → iterate — with every step timed and captured in an append-only transcript. The HTTP surface is four routes (`POST /agent/run`, `GET /agent/run/:id`, `POST /typecheck`, `GET /healthz`) served by a plain URL switch (zero router deps), with run state in an isolate-memory `Map` and 404s that honestly report isolate-lifetime state. Three pluggable seams — `LLMProvider` (mock default, OpenAI-compatible opt-in), `Typechecker` (typescript package now, tsc-rs slot later), `SandboxRuntime` (QuickJS-WASM only — workerd forbids host `eval`/`new Function`, so the WASM interpreter is not a choice but the only path) — keep each swap point isolated behind narrow interfaces.

The stack research (STACK.md) pins exact, npm-verified versions: wrangler 4.149.0 (bundling workerd 1.20261006.1), typescript from the pure-JS line, quickjs-emscripten-core 0.32.0 + a **sync** singlefile-or-wasmfile variant (asyncify costs 2× size/~40% speed for capabilities the loop must not use anyway), vitest 4.1.11 + the renamed `@cloudflare/vitest-plugin` 1.4.0. Two verified landmines shape everything: npm's `latest` typescript is now **7.x, the Go-native tsgo** — it cannot execute in-process inside workerd — and workerd's security model (no fs, no dynamic eval, frozen `Date.now()` during sync execution, 128 MB shared JS+WASM isolate memory) invalidates several "natural" designs (disk-backed compiler hosts, wall-clock-only sandbox deadlines, host-side eval shortcuts).

The features research (FEATURES.md) places iso-agents squarely in the **in-isolate school** (TS Playground/`@typescript/vfs`, quickjs-emscripten, Cloudflare Code Mode) versus the microVM school (e2b, Vercel Sandbox). That camp choice yields the governing product principle: maximize **observability of the loop** (transcript, structured diagnostics, per-step timings, machine-readable terminal status) rather than environment richness. Table stakes are the loop itself, transcript-from-iteration-1, structured `{message,file,line,col,code}` diagnostics, timeout/memory guardrails, a stateful mock LLM (broken v1 → fixed v2, or the demo is fake), and `maxed-out` as a distinct terminal status. Differentiators worth building: a second trivial Typechecker impl to prove the seam, `/typecheck` N-run median stats, and read-time per-iteration diffs. Anti-features (auth, persistence, UI, multi-file/module resolution) are all correctly declared out of scope in PROJECT.md.

The pitfalls research (PITFALLS.md) is the operational manual: the #1 trap is that `npm i typescript` no longer installs a workerd-runnable compiler (pin the pure-JS line and assert at boot); the #2 is unresolvable lib `.d.ts` files (inline them as text; `getDefaultLibFileName` returns a *name*, not contents). Sandbox-side, QuickJS aborts from guest stack overflow are **uncatchable and poison the whole WASM module** (fresh single-use contexts, `setMaxStackSize`, dispose discipline), interrupt handlers only poll at loop back-edges (counter-based handler as hard backstop — `Date.now()` freezes during sync execution), `setMemoryLimit` under-enforces totals (issue #271, reproduced on workerd), and the 128 MB isolate cap means tsc AST churn can silently evict the run store mid-session. The loop-side traps are messy LLM output (multi-tier extraction), prompt bloat/non-convergence (windowed history, stale-diagnostic early exit), and a too-perfect mock that never exercises the fix loop. One conflict requires a planner decision: STACK recommends **typescript@6.0.3** (verified pure-JS, tarball-inspected) while PITFALLS recommends pinning **typescript@~5.9.3** — both agree 7.x is unusable; see Gaps.

## Key Findings

- **Stack:** wrangler 4.149.0 (`wrangler dev` = real workerd, no account) + typescript pure-JS line (6.0.3 per STACK, ~5.9.3 per PITFALLS — spike decides; **never `npm i typescript` unpinned: latest is native tsgo 7.x, unrunnable in-isolate**) + quickjs-emscripten-core@0.32.0 with a **sync** variant + vitest 4.1.11 / `@cloudflare/vitest-plugin` 1.4.0; everything else (router, LLM client, run store, validation) is zero-dependency hand-rolling.
- **Architecture:** thin router → orchestrator owning the loop state machine → three injected seams (LLMProvider, Typechecker, SandboxRuntime) with in-memory VFS as single source of truth, transcript appended per iteration from step one, per-step `performance.now()` + `Date.now()` timings, and a fail-fast gate that skips sandbox execution whenever type errors exist.
- **Critical pitfall:** `npm install typescript` now resolves to the native-only TS 7 (tsgo) — the in-isolate type-check plan silently dies at integration; pin the pure-JS line explicitly, verify via boot-time assertion (`ts.createProgram` exists, `lib.es5.d.ts` resolvable from the VFS), and document why the pin exists.
- **Sandbox safety limits must exist before the first real loop run** — an LLM-written `while(true){}` without `shouldInterruptAfterDeadline`/counter interrupt hangs `wrangler dev` unrecoverably; and guest stack overflows abort the entire WASM module (uncatchable, poisons cached instances) → fresh single-use contexts per iteration, `setMaxStackSize`, dispose in `finally`.
- **workerd platform semantics invalidate naive designs:** no filesystem (inline lib `.d.ts` as build-time text; hand-rolled CompilerHost, never `ts.sys`), `Date.now()` frozen during synchronous execution (op-count interrupt handler as hard backstop; timings may need dual-clock verification), `setMemoryLimit` under-enforces (enforce own budgets: ≤20KB generated source, ≤5 iterations), and the 128 MB isolate is shared JS+WASM so tsc AST churn can evict the run store — memoize lib SourceFiles, drop per-iteration programs.
- **The mock LLM must be deliberately imperfect and stateful** — scripted broken-first iteration (with markdown fences, to exercise extraction) then error-driven fixes — or the loop's actual deliverable (diagnostics feedback → green) is never tested; feature principle throughout: observability of the loop over environment richness.
- **Testing posture decision up front:** STACK recommends the renamed `@cloudflare/vitest-plugin` (in-workerd tests); PITFALLS 17 warns of pool-integration friction and recommends curl-against-`wrangler dev` E2E + pure-Node unit tests — pick one primary (suggested: curl-first, one plugin smoke test) before writing tests.

## Implications for Roadmap

Suggested phase structure (each phase independently curl-verifiable; ordering follows the dependency chain in FEATURES.md with the two riskiest integrations spiked first):

**Phase 1 — Scaffold + integration spikes.** wrangler.jsonc (compat date, `Text` rule for lib `.d.ts`), 4-route switch router, JSON error envelope, `/healthz` (version, TS version, provider, `instanceId`), in-memory run registry + status enum. Spikes: (a) typescript-in-workerd — bundle + run `createProgram` with an in-memory host inside real workerd; resolves the **6.0.3 vs ~5.9.3 pin** and the **nodejs_compat** question; (b) QuickJS variant loading — singlefile-embed vs `import wasm + newVariant({ wasmModule })`.
*Addresses features:* task intake skeleton, healthz, run registry/IDs. *Avoids pitfalls:* 1 (TS7), 3 (Node builtins), 13 (WASM loading), 14 (bundle/startup), 15 (`instanceId` from day one), 18 (error envelope). *Research flags:* STACK: "Not yet executed inside real workerd — first build task must confirm"; singlefile bundling is MEDIUM confidence. *Rationale for going first:* either spike failing invalidates the architecture — cheapest possible moment to learn that.

**Phase 2 — Type-check core (the thesis).** VFS + fully hand-rolled CompilerHost + minimal lib `.d.ts` set inlined as text + `Typechecker` interface + typescript-package impl + structured diagnostics formatter (flatten, line/col, dedupe, cap ~10) + `POST /typecheck` with wall-ms (+N-run median if cheap) + a trivial second impl (`transpile-only`/`noop`) to prove the seam. Include the timing-fidelity busy-loop micro-test here.
*Addresses features:* structured diagnostics, in-memory VFS, `/typecheck` + stats, per-step timing foundation, typechecker seam (tsc-rs story). *Avoids pitfalls:* 2 (lib files), 3 (pure APIs only, dry-run bundle check), 9 (memoized lib SourceFiles), 16 (diagnostic hygiene), 19 (dual-clock timing). *Research flags:* verify `typecheckMs` ≠ 0 for real checks; decide builder-program/`oldProgram` reuse vs documented-deferred incremental.

**Phase 3 — Sandbox executor.** Lazy QuickJS module init, fresh single-use context per execution, counter-based interrupt + deadline, memory limit + own budgets, max stack size, console shim, in-sandbox assertion harness (`vm.dump` results back), sync-only guest lint (reject `await`/`setTimeout`/`fetch`/imports), dispose discipline, DEBUG_SYNC leak test, `while(true){}` integration test returning structured timeout.
*Addresses features:* safe sandbox execution under no-eval rules, in-sandbox assertion harness, structured sandbox failures (never thrown 500s). *Avoids pitfalls:* 4 (abort/poisoned module), 5 (infinite loops), 6 (memory accounting), 7 (asyncify reentrancy), 8 (host-eval grep in CI), minor handle-leak/console items. *Research flags:* hard requirement — limits precede any real loop run (FEATURES dependency graph).

**Phase 4 — Mock LLM + agent loop.** `LLMProvider` seam; stateful mock (broken-first-shot with fences + instant-green modes); OpenAI-compatible impl typed but untested; loop state machine with fail-fast typecheck gate, `maxIterations` (≤5), run-level deadline, windowed prompt history, stale-diagnostic early exit, transcript capture from iteration 1, full status enum (`green | typecheck-failed | tests-failed | sandbox-timeout | deadline-exceeded | maxed-out | internal-error`).
*Addresses features:* multi-iteration loop with error feedback, iteration transcript, guardrails, deterministic mock, machine-readable status. *Avoids pitfalls:* 10 (messy output extraction), 11 (prompt bloat/non-convergence), 12 (too-perfect mock), residual 5/6 via source-size caps. *Research flags:* test asserting `iterations >= 2` for the broken-first-shot fixture.

**Phase 5 — Inspection, stats, demo.** `GET /agent/run/:id` (honest 404 with isolate-restart reason), `?download=1` artifact, read-time per-iteration diffs (no diff dep), `/typecheck` N-run median stats, `demo.sh` happy path, README documenting the tsc-rs seam (native-only, no WASM today), no-auth note, frozen-clock/memory caveats, `/healthz` boot self-test.
*Addresses features:* run inspection endpoint, differentiators (stats, diffs, artifacts), tsc-rs context documentation (PROJECT active requirement). *Avoids pitfalls:* 15 (honest 404), 18 (curl `--max-time`, JSON-always). *Research flags:* defer SSE streaming and incremental program reuse (document as the tsc-rs payoff instead — FEATURES explicitly recommends this).

**Ordering rationale:** strict dependency chain (registry → VFS/checker → transpile/sandbox → loop → inspection endpoints); the two integration risks that could kill the design (typescript-in-workerd, QuickJS-in-workerd) are consumed as Phase 1 spikes before anything composes on them; sandbox guardrails land before the loop exists so the first real iteration is already bounded; `/typecheck` lands before the loop so its timings — the project's quantitative raison d'être — are measurable standalone from Phase 2 onward.

## Gaps to Address

1. **TypeScript pin conflict (decision required, build-phase spike):** STACK recommends `typescript@6.0.3` (tarball-verified pure JS, "maintained end of the JS line," API-identical for our use; 5.9.3 as fallback) while PITFALLS says pin `typescript@~5.9.3` (measured 8.7MB + 3.3MB libs). Both agree TS 7.x is native-only and forbidden. The planner must pick one and verify in the Phase 1 spike (bundle + in-workerd `createProgram` + lib resolvability), with a boot-time version/API assertion either way so an accidental upgrade fails loudly.
2. **QuickJS variant packaging conflict (spike):** STACK recommends `@jitl/quickjs-singlefile-browser-release-sync` (WASM base64-embedded → no runtime `.wasm` resolution; MEDIUM confidence on exact bundling); ARCHITECTURE/PITFALLS follow the official Cloudflare example — copy the `.wasm` into `src/`, `import wasm from './quickjs.wasm'`, `newVariant(base, { wasmModule })`. Same sync engine either way; wasmfile-import is the documented fallback. Phase 1 spike decides.
3. **nodejs_compat vs compatibility_date:** STACK's config deliberately omits `nodejs_compat` (so typescript's `isNodeLikeSystem()` guard stays false); PITFALLS notes nodejs_compat is *default-on* at compatibility_date ≥ 2026-08-04 — which STACK's pinned `2026-09-01` exceeds. Verify in the spike whether the flag is actually off at that date and whether typescript's Node sys branch activates; the pure-APIs-only + fully-hand-rolled-host rule is the safety net regardless.
4. **CompilerHost construction style (minor conflict):** ARCHITECTURE's snippet patches `ts.createCompilerHost(options)` overrides; PITFALLS 3 says never touch `ts.createCompilerHost` and hand-roll the complete host object. Conservative choice: fully hand-rolled; spike confirms which works under the pinned TS version.
5. **Testing posture (decide up front, Pitfall 17):** vitest-plugin in-workerd tests (STACK, current renamed package) vs curl-against-`wrangler dev` primary E2E (PITFALLS). Suggested resolution: pure-Node unit tests + curl-script E2E as primary, at most one vitest-plugin end-to-end smoke; record the decision before writing tests.
6. **Timing fidelity in workerd (Pitfall 19, medium confidence):** frozen `Date.now()` during sync execution may make `typecheckMs` read ~0. Phase 2 must include the busy-loop micro-test and the dual-clock (`performance.now()` + `Date.now()`) strategy before trusting any headline numbers.
7. **Memory headroom unmeasured:** TS (~10MB bundled) + QuickJS WASM + per-iteration AST churn inside the shared 128 MB isolate is risk-flagged, not measured. Prototype-scale acceptable; log `computeMemoryUsage()` in dev and watch for isolate-eviction 404s (Pitfall 6/15 detection).
8. **CPU-limit applicability:** free-plan 10 ms/request is production-only — `wrangler dev` does not enforce it (official), so local latency measurement works; note in docs so nobody "fixes" a non-problem locally.
